# 0.16.1.dev1 조회 중복 제거

설치된 0.16.0 후보에서 137개 기록·77개 작업이 쌓인 상태를 조회할 때, 같은 대용량
문서를 반복 복원하는 비용을 확인했다. 현재 변경은 소스에만 반영했으며 기본 앱
0.15.0과 설치 후보 0.16.0은 바꾸지 않았다.

## 구현과 검증

아티팩트 소유자 조회는 이미 검증한 작업의 원래 문서를 같은 호출 안에서 재사용한다.
입력 descriptor의 중첩 메타데이터는 별도로 복사해 기존 호출자의 변경 격리를 유지한다.
케이스 목록은 모든 과거 기록을 검증한 뒤 선택한 최신 기록을 다시 가져오지 않고
기존 계약·권한·원본·아티팩트 검증 함수에 전달한다. 공개 상세 조회는 매번 새로 읽는다.
영속 캐시, 미검증 메타데이터 필터, 저장 스키마·API·물리 계산 변경은 없다.

관련 Registry 시험 110개와 케이스 서비스·API·화면 투영 시험 79개가 통과했다.
독립 검토에서는 기존 검증 순서와 참조 공유 동작을 확인했다. 두 묶음의 수를 전체
플랫폼 회귀나 고유 물리 시험 수로 사용하지 않는다.

| 따로 측정한 작업 | 기존 중앙값 | 수정 후 중앙값 | 범위 |
| --- | ---: | ---: | --- |
| 아티팩트 소유자 조회 | 1.118초 | 0.568초 | 논리 크기 약 5.14 MB인 대표 요청 하나 |
| 케이스 목록 조회 | 2.539초 | 1.936초 | 약 21.79 MB 케이스를 포함한 최신 케이스 두 개 |

각 조건에서 따뜻한 파일 시스템으로 3회 측정했다. 전체 응답 바이트·연결 입력과 복사
DB·2,388개 Blob이 같음을 확인했다. 이는 개별 작업의 측정값이며 HTTP, 동시 부하,
전체 화면 또는 고객 환경의 성능 보장은 아니다. 새 소스의 Wheel·설치 실행·전체 회귀는
아직 검증하지 않았다.

## 다음 범위

현재 retained ISP 화면은 소스·재처리·후보 목록을 별도로 요청하면서 전체 작업 이력을
반복 복원한다. 다음 제안은 한 번 검증한 작업 목록에서 표시용 요약을 함께 만드는
GET 경로다. 각 상세·실행 준비·내보내기는 원본 바이트를 계속 새로 검증해야 한다.
현재 소스 목록은 메타데이터 탐색이며 RAW 바이트 검증 완료를 뜻하지 않는다.

dev1 검증 당시 이 통합 조회는 **미구현 제안**이었다. 후속 dev2 구현과 검증 범위는
[통합 목록 조회](camera-platform-retained-isp-workbench.md)에 별도로 기록한다.
동일 표시값·상세 해시·검증 실패 동작, 변경된
원본과 완료 증거의 검출, 메모리·응답 크기·동시 부하를 확인해야 한다. 전체 이력이
커지는 문제의 완전한 해결도 별도 과제다.
[후속 설계](../reports/camera_platform/read-efficiency-v0161/bootstrap-followup-plan.md)를 따른다.
